# impl-from-ddoc

Design Doc の内容をレビューし、必要に応じてユーザーにインタビューしながら実装を進める。実装完了後、ユーザーの承認を得てからサマリーを ddoc に追記する。

## ワークフロー

### Step 1: 対象の Design Doc を特定する

現在のセッションで make-ddoc を使った場合など、対象の ddoc が会話から自明であればそれを使う。

自明でない場合は `docs/design-doc/` のファイル一覧を表示してユーザーに選択させる：

```bash
ls docs/design-doc/*.md | sort
```

### Step 2: Design Doc を読み込む

対象の ddoc ファイルを読み込み、以下を把握する：

- **概要・目標・非目標**: 何を作るか、何を作らないか
- **設計**: API・DB・フロントエンドの変更内容
- **変更ファイル一覧**: どのファイルに何をするか
- **実装ステップ**: 依存関係を考慮した実装順序
- **未解決事項**: 決まっていないことがあれば実装前に確認が必要

### Step 3: 不明点をインタビューする（必要な場合）

ddoc を読んで実装に着手する前に不明・未確定の点があれば、**まとめて一度に**ユーザーへ確認する。

確認が必要な例：
- ddoc の「未解決事項」に記載されている決定待ちの事項
- 変更ファイルの記載が曖昧で実装方針が定まらない箇所
- 複数の実装方法がありうる設計上の選択肢

実装が進む中で追加の疑問が生じた場合も都度ユーザーへ確認してよい。ただし早い段階で質問できるのが最も望ましい。

### Step 4: 実装する

ddoc の「実装ステップ」に記載された順序で実装を進める。

**実装方針：**
- CLAUDE.md のアーキテクチャパターン・命名規則・コーディングスタイルに従う
- 変更ファイル一覧に記載のないファイルへの変更が必要な場合は、その理由をユーザーへ説明する
- 実装中に設計上の問題や矛盾に気づいた場合は、実装を止めてユーザーに報告する

**型チェック・動作確認：**
スコープと編集内容に応じて判断する。実行すべきコマンドや手順は `CLAUDE.md` の記載に従う。ユーザーが必要と判断すれば追加の確認を指示してもらう。

コミットや GitHub 上の操作は、ユーザーから明示的に指示があった場合のみ行う。

### Step 5: 実装完了を報告してユーザーの確認を待つ

実装が完了したら、以下を報告する：

- 実装した内容の概要
- 変更したファイルの一覧
- 型チェック・動作確認の結果（実行した場合）
- 気づいた点・懸念点・ddoc と異なった点

ユーザーから承認（「OK」「問題ない」「サマリーを追記して」など）が得られるまで待つ。

### Step 6: Design Doc にサマリーを追記する

ユーザーの承認後、対象の ddoc ファイルの末尾に以下のテンプレートでサマリーを追記する。

サマリーは日本語で記述する。ddoc を書いた時点よりも実装時点のほうが得られる情報が多いため、実装して初めてわかったことも積極的に書く。

```markdown
---

## 実装サマリー

> **実装日**: YYYY-MM-DD

### 変更ファイル

- `path/to/file` — [何をしたか]

### 実装内容

[実装でやったことの概要。ddoc の設計通りに進んだか、変更点があれば理由も含めて記述する]

### 確認・検証

[型チェック・動作確認など実施した検証内容と結果]

### 気づき・備考

[実装中に気づいたこと、ddoc には書かれていなかった情報、今後の注意点など]
```

サマリーの追記が完了したらスキルを終了する。
