# make-ddoc

ユーザーへのインタビューを通じて、AI Agent が実装に着手できるレベルの詳細を持つ Design Doc を作成する。

## ワークフロー

### Step 1: コンテキストを把握する

`CLAUDE.md` があれば読んで、技術スタック・ディレクトリ構成・アーキテクチャパターンを把握する。インタビュー内容の補完や、不足情報の判断に使う。

引数に GitHub issue 番号 / URL や対象ファイルが渡されていれば、`gh issue view` や対象ファイルの該当箇所を実際に読んで、変更規模をおおまかに見積もる材料を集める。

### Step 2: 修正規模を見積もり、Design Doc 作成の要否を判断する

Design Doc は実装方針のズレや手戻りを防ぐためのものなので、修正規模が小さく方針に迷う余地がない場合は作らないほうが効率的。集めた情報をもとに、以下の基準でユーザーに確認する。

**Design Doc 不要と判断してよいケース（典型例）:**

- 1〜2 行程度の typo / オペレータ間違い / 演算子修正
- 純粋なリネーム・依存パッケージのバージョン更新
- 単一ファイル内で完結する明確なバグ修正で、原因と対処が観察事実から一意に決まるもの
- 設計判断や複数選択肢の検討が発生せず、方針インタビューが空振りに終わるもの

**Design Doc を作るべきケース（典型例）:**

- 新機能・新エンドポイント・新ページの追加
- 複数ファイル・複数レイヤーにまたがる変更
- アーキテクチャやインターフェースに影響する変更（API シグネチャ・DB スキーマ・公開関数の変更など）
- 実装方針に複数の選択肢があり、事前に決めておきたいもの
- リファクタリングで影響範囲を切り分けたいもの

**判断と確認の流れ:**

1. 規模感を 1〜2 文で要約してユーザーに伝える（例: 「`api/db/repositories.rb:208` の `...` を `..` にする 1 行修正です」）
2. **Design Doc 不要と判断したケース**: 「Design Doc は省略して直接実装に進めるのが良さそうですが、それで進めますか？」と確認する。ユーザーが了承したらこのスキルは終了し、直接実装フェーズへ進む（`/impl-from-ddoc` は使わない）
3. **Design Doc を作るべきケース**: そのまま Step 3 のインタビューに進む
4. ユーザーが「規模に関わらず Design Doc を作って」と明示した場合は、判断を上書きして必ず作る

### Step 3: 連番を決定する

`docs/design-doc/` ディレクトリの既存ファイルを確認し、最大の連番 + 1 を次の番号とする。ファイルがなければ `0001` から始める。

```bash
ls docs/design-doc/*.md 2>/dev/null | sort | tail -1
```

ファイル名の形式は `docs/design-doc/[%04d]-[scope]-[feat].md`（例: `docs/design-doc/0003-api-add-payment-method.md`）。

### Step 4: ユーザーにインタビューする

以下の質問を **まとめて一度に** 聞く。回答があいまいな部分は深掘りしてよい。

**基本情報（必須）:**
- 何を作るか（機能の概要）
- スコープ（`api` / `front` / `db` / `infra` など、複数可）
- 機能名（ファイル名に使う短い英語スネークケース）

**設計の詳細（分かる範囲で）:**
- API の変更: エンドポイント・HTTPメソッド・リクエスト/レスポンスの形
- DB の変更: テーブル・カラムの追加/変更
- フロントエンドの変更: ページ・コンポーネント・状態管理
- 変更が必要なファイル（分かる場合）

**スコープの境界:**
- 目標（何が達成されれば完了か）
- 非目標（今回はやらないこと）
- 未解決の懸念点や決まっていないこと

### Step 5: 不足情報を補完する

`CLAUDE.md` の内容とユーザーの回答を照合して、実装に必要なのに回答が抜けている項目があれば追加で確認する。

補完の判断例:
- 認証が必要な API なのに認証方式が未回答
- DB の変更があるのにマイグレーション方針が未回答
- フロントエンドの変更があるのに型定義の扱いが未回答

### Step 6: Design Doc を生成して保存する

`docs/design-doc/` ディレクトリがなければ作成し、以下のテンプレートに従ってファイルを生成する。

変更がないセクション（API 変更がない場合の「API 設計」など）は省略してよい。

「変更ファイル一覧」と「実装ステップ」は、AI が実装に着手できる粒度で書くことが重要。ファイルパスは具体的に、ステップは依存関係の順序を意識して書く。

ファイルを保存したら、ユーザーに `/impl-from-ddoc` で実装に進めることを案内する。

---

## Design Doc テンプレート

```markdown
# [%04d] [機能名]

> **scope**: [scope] | **date**: [YYYY-MM-DD]

## 概要

[1〜2文で機能を説明する]

## 目標

- [達成したいこと]

## 非目標

- [今回の範囲外にすること]

## 設計

### API 設計

[変更・追加するエンドポイントを記述する]

| メソッド | パス | 説明 |
|---------|------|------|
| GET | /api/v1/xxx | ... |

**リクエスト:**
```json
{}
```

**レスポンス:**
```json
{}
```

### データモデル

[テーブル・カラムの変更を記述する]

```sql
ALTER TABLE xxx ADD COLUMN ...;
```

### フロントエンド設計

[コンポーネント構成・ルート・状態管理を記述する]

## 変更ファイル一覧

実装時に変更が必要なファイル。AI が実装に取り掛かれるよう具体的に書く。

- `path/to/file` — [何をするか]

## 実装ステップ

依存関係を考慮した順序で書く。各ステップは独立したコミット単位になるとよい。

1. [最初にやること]
2. [次にやること]

## 代替案

[検討したが採用しなかった案と、採用しなかった理由]

## 未解決事項

- [決まっていないこと]
```
